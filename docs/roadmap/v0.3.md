# Ghostly v0.3 — Repository testing from the IDE

Install with `npm install -g @ghostly-io/cli`, `ghostly install`, and `ghostly up`. Open a trusted workspace in an MCP-enabled IDE and ask “Create the tests that would add the most value to this repo.” Ghostly should inspect the source and existing tests, prioritize behavior with evidence, then generate and run ordinary versionable test files using the project's test stack.

## IDE workflow and contracts

Use the configured MCP workspace root (or process working directory). Scope paths are relative to that root. An explicit plan request inspects files without writing or executing. An explicit create request authorizes generation and local execution within the requested scope. An unsupported stack or ambiguous convention returns a reason and a next step. Existing browser and project MCP tools keep their current contracts.

| Tool | Inputs | Output and status |
| --- | --- | --- |
| `ghostly_init` | `mode` (`plan` or `apply`), optional relative `module` | With no module, discover and rank up to three unit cases. Apply selects one supported case with no apparent coverage or reports that more information is needed. With a module, use the same scoped workflow as `ghostly_test_unit`. Multi-layer dispatch is pending. |
| `ghostly_test_unit` | `mode`, required relative `module` | Generate and run a unit test from an independent written expectation for a named TypeScript export. |
| `ghostly_test_integration` | `mode`, required relative `module` | Generate and run one documented numeric operation through its direct local TypeScript dependency. Uses the same verified `tsx` and `node:test` setup as unit tests. API and persistence adapters are pending. |
| `ghostly_test_e2e` | `mode`, flow `name`, loopback `baseUrl`, `route`, `steps`, `acknowledgement`, `persistence` | Plan or generate and run a Playwright persistence test. Steps use stable test IDs and synthetic data. Requires both visible save acknowledgement and a visible record after reload. |
| `ghostly_audit_security` | Optional relative `scope` | Run a bounded, read-only hygiene review of supported source, dependency declarations and configuration. Report repository-relative evidence, impact, mitigation and confidence without source excerpts or credential values. |

The analysis role inventories stack, tests and conventions. Planning records the behavior, source location, why it matters and the required assertion. Generation writes only the selected file(s) within scope. Verification reports the baseline when available, executes the tests and records the command and outcome. The IDE report shows each role's actions. An assertion failure determines failure. A judge can diagnose and flag missing evidence.

## Existing suites and new projects

Detect runners, fixture conventions, path and naming before making edits. Establish a baseline when possible and report pre-existing failures separately. Preserve existing tests and configurations. If there is no suite, propose coverage for critical behavior, explain each choice and use a verified stack configuration. The first delivery targets TypeScript on Node with an existing `tsx --test` script and one explicit test glob. Other Node layouts, TypeScript and React conventions need fixture and client validation before being marked supported.

## Run repository discovery

From this repository, run `node --test packages/mcp-server/test/unit-workflow.test.mjs`. The fixtures start the MCP server over stdio using the MCP SDK. They verify scoped calls, repository discovery without a module, apparent coverage, plan-only behavior, a separately reported pre-existing failure, and frozen tests that detect implementation-only regressions. To exercise the CLI-bundled entry, build with `pnpm --filter @ghostly-io/cli build` and run the same test with `GHOSTLY_TEST_PACKAGED_MCP=1` in the environment.

For an agent trial, point Ghostly's MCP process at a trusted workspace through `GHOST_TARGET_PROJECT_ROOT`. Use the local development server entry or a CLI build from this source. Create a package with a locally installed `tsx` dependency, the exact script `"test": "tsx --test test/*.test.ts"`, and an existing `test/` directory. Put this in `src/eligibility.ts`:

```ts
/** Returns true exactly when age is at least 18. */
export function isEligible(age: number): boolean {
  return age >= 18;
}
```

Ask the MCP-enabled agent to plan tests for the repository or to create and run its highest-priority uncovered unit test. These map to `ghostly_init` with `{"mode":"plan"}` or `{"mode":"apply"}`. Pass `"module":"src/eligibility.ts"` to scope either testing tool. Apply returns the baseline and generated result separately, the assertion and changed paths, and the replay command:

```sh
node --import tsx --test test/eligibility.ghostly.test.ts
```

Discovery prefers uncovered documented boundary cases, then uncovered documented numeric examples. The report lists the behavior, source line, proposed assertion and apparent coverage for each candidate. Expected values come from a narrow written contract or `@example`. An export with a plausible behavior but no independent expectation is reported with no assertion. Plan reads source and tests without executing them.

The verified stack is Node 20.14, TypeScript, tsx, and Node's test runner. The fixture uses an MCP SDK client over stdio. Discovery is bounded to simple TypeScript exports and flat `.test.ts` files in the configured directory. Its coverage heuristic recognizes direct assertions on named relative imports, including aliases. A recognized import with no matching assertion is ambiguous. Coverage through wrappers, barrel exports or dynamic imports can escape detection. Generated tests and existing suite files are preserved. Additional runners, persisted evaluation reports and model accounting are pending.

## Verification and evaluation

- Codex CLI verified the CLI-bundled Ghostly server over standard MCP stdio with separate natural-language requests to plan and to create the highest-value unit test. Both tool calls omitted `module`. The plan distinguished a covered discount case, an undocumented bonus candidate and an uncovered documented eligibility boundary. Apply created `test/eligibility.ghostly.test.ts` and both the baseline and the new test passed. The server uses the same contract with other MCP clients.

- Run the generated files from Git and CI using ordinary test commands, with deterministic assertions and no model dependency for results.
- Add Playground fixtures for empty and existing suites. Generate the persistence test once and freeze the same file across three variants. Healthy save must pass. A save that appears successful and loses the record on reload must fail at the required persistence assertion. A UI-only change with equivalent behavior should pass.
- Record tool, roles, selected cases, changed files, assertions, result, duration and model usage when supplied. Evaluate false greens, intermittent results, redundant coverage and cost.
- Test unchanged existing MCP tools, empty and existing suites, repeat invocation, assertion failures and unsupported configuration. Record verified combinations of stack, runner and MCP client.

## Run an integration test in CI

In the supported workspace, add a public operation that documents its expected result and calls a named import from another local TypeScript module. For example, `src/checkout.ts` can call a real discount module:

```ts
import { discount } from "./pricing.ts";

/** @integrationExample checkoutTotal(200) => 180 */
export function checkoutTotal(subtotal: number): number {
  return subtotal - discount(subtotal);
}
```

Call `ghostly_test_integration` with `{"mode":"plan","module":"src/checkout.ts"}` to inspect the source evidence, imported dependency and assertion. Apply creates `test/checkout.ghostly.integration.test.ts` and reports the baseline and generated test separately. For example, `baseline.status: failed` with `verification.status: passed` identifies a pre-existing suite failure. A change in the dependency can fail the generated assertion while the baseline stays green.

Commit the generated test and its source dependencies. In CI, install dependencies from the target project's lockfile, then run the reported command from its root:

```sh
node --import tsx --test test/checkout.ghostly.integration.test.ts
```

The test runs in Node with an ordinary assertion and uses its exit status. No Ghostly server, MCP client, model or credentials are needed. Run the existing suite as its own CI step if you need separate results. This delivery supports direct named relative `.ts` imports and a single numeric return expression that calls the dependency. Service setup, databases and custom integration runners remain open.

## Verify browser persistence

`ghostly_test_e2e` uses the same TypeScript test directory and requires Playwright in the target package. Supply an HTTP(S) loopback origin, a starting route, and ordered `click` and `fill` steps that refer to existing `data-testid` values. Stable test IDs let the test follow a control when its position or label changes. Each check supplies a `testId` and `text`. The acknowledgement checks the visible confirmation before reload. The persistence check looks for exact visible record text inside its stable container after reload. Use synthetic fixture values in fill steps because they are written to the test.

The stdio fixture at `packages/mcp-server/test/e2e-workflow.test.mjs` drives the actual Playground's client-creation flow. Both the source and CLI-bundled MCP servers passed the fixture in Chromium, including independent replay. The fixture saves one test and reuses its unchanged bytes on each variant:

| Playground variant | Expected result |
| --- | --- |
| Healthy save | Visible acknowledgement and record after reload. |
| Fake save | Visible acknowledgement, followed by `PERSISTENCE_ASSERTION` because the record was discarded. |
| Healthy alternate layout | Same assertions pass after moving and relabeling the create button while keeping its test ID. |

With Chromium installed for Playwright, run the fixture from the Ghostly repository with `node --test packages/mcp-server/test/e2e-workflow.test.mjs`. To run against the CLI-bundled MCP server, build the CLI and set `GHOSTLY_TEST_PACKAGED_MCP=1`. The fixture starts local Playground servers on loopback and resets the in-memory data between runs. The generated test runs in Node with the target application's origin supplied through `GHOSTLY_E2E_BASE_URL`. For example, in a POSIX shell in the target project:

```sh
GHOSTLY_E2E_BASE_URL=http://127.0.0.1:4700 node --import tsx --test test/client-persistence.ghostly.e2e.test.ts
```

In CI, start the test application before running that command and provide Chromium. The replay needs no model and does not run the rest of the suite. This delivery covers the Playground persistence scenario with explicit steps and stable test IDs. Automatic E2E discovery, additional interaction types and broader runner support are still open.

The repository stays on the locked Playwright 1.59.1 version for this delivery. [Playwright's page API](https://playwright.dev/docs/api/class-page#page-get-by-ref) documents `getByRef` as added in 1.64, with references scoped to the latest AI accessibility snapshot. Keep those references out of persisted test files. Evaluate an upgrade separately against the frozen Playground case and the existing selector regression suite before adopting live references.

## Review local security hygiene

Call `ghostly_audit_security` with `{}` for the workspace or `{"scope":"src"}` for a relative file or directory. It returns findings and coverage in the MCP response. Each finding includes a rule, repository-relative file and line, confidence in the observation, conditional impact and a mitigation. The tool runs no target code, makes no network requests and writes no report files.

| Check | What it observes |
| --- | --- |
| Possible embedded credential | Common credential keys assigned a quoted literal in supported JavaScript, TypeScript, JSON, YAML or Dockerfiles. Common placeholders are excluded. Review matches locally to determine whether the values are real. |
| Configuration posture | Explicit root users in Dockerfiles and explicit Node TLS verification disabling settings. The tool does not infer which stage or configuration is deployed. |
| Dependency hygiene | Floating `*`, `latest` and `next` declarations in package manifests, plus presence of a supported npm, pnpm, Yarn or Bun lockfile in the package directory or its ancestors. Lockfile contents, transitive versions and advisory data are outside this check. |

Traversal excludes hidden and vendor/generated paths, common credential-store filenames, symbolic links and junctions. It inspects at most 1,000 directory entries, 200 files, 2 MiB of text, 128 KiB per file, 16 levels below the selected directory and 50 findings. A `partial` response reports gaps such as size limits or unreadable content. A `complete` response means the configured checks finished within scope. Validate the behavior through stdio with `node --test packages/mcp-server/test/security-audit.test.mjs`. The source and CLI-bundled server passed the Windows fixture, including rejection of a junction that pointed outside the workspace.

## Delivery order

1. First unit slice through both MCP entries. Use a single scoped TypeScript module and a numeric example declared in source. Derive the test path from the runner's configured glob. Exercise planning, generation and execution over MCP stdio.
2. Implemented repository-wide discovery and direct-assertion deduplication for the verified TypeScript stack. Support for projects without a test configuration, other runners and more clients remains open.
3. Implemented local TypeScript module integration with a documented expectation and a model-free CI command. The MCP fixture checks failure attribution in both directions and verifies the same test detects a regression in the dependency.
4. Implemented deterministic Playwright generation and frozen Playground persistence evaluation. A Playwright upgrade and live `getByRef` evaluation remain separate work.
5. Implemented a read-only defensive hygiene report with redacted evidence, scope controls and coverage counts.

Open decisions include initial framework/client matrix, support for workspaces and custom fixtures, prioritization with incomplete evidence, and storing evaluation telemetry. v0.4 reserves multiple judges, hosted multi-user collaboration, scheduled runs and an optional Go desktop app reusing the web dashboard.
